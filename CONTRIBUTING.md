# Contributing to Tabar

Thanks for your interest in improving Tabar! This guide covers the conventions and the
local workflow.

## Getting started

```bash
git clone https://github.com/simtabi/tabar.git
cd tabar
npm install
npm run styles    # compile SCSS -> dist/tabar.css + src/styles.js (needed before tests)
npm test          # vitest + happy-dom (pretest runs `styles` for you)
npm run typecheck # tsc --noEmit against types/
npm run lint      # eslint
npm run build     # esbuild -> dist/ (all entry points)
```

Run the site through the local server — ES modules don't load over `file://`:

```bash
npm run demo      # builds the site, then serves http://localhost:8080/
                  # landing at /, playground at /playground.html
```

Try the terminal renderer / CLI:

```bash
node examples/cli.js
printf '30 100\n80 100\n100 100\n' | node bin/tabar.js --total 100 --label Build
```

## Project layout

| Path | Purpose |
|------|---------|
| `src/tabar.js` | Core library — the `Tabar` class (zero runtime dependencies). |
| `src/group.js` | `TabarGroup` — a parent task with child bars (`@simtabi/tabar/group`). |
| `src/terminal.js` | Terminal/ANSI renderer; `src/node.js` is the Node entry (`/node`). |
| `src/element.js` / `src/react.js` | `<tabar-bar>` Web Component and `useTabar` hook. |
| `src/attrs.js` | Shared attribute coercion for `<tabar-bar>` and plain-mount `data-tabar-*`. |
| `bin/tabar.js` | The `tabar` CLI (renders progress piped on stdin). |
| `src/tabar.scss` | Style source of truth. **Edit this**, not the generated CSS. |
| `src/styles.js` | Generated by `npm run styles` — the runtime CSS string. Do not edit. |
| `types/*.d.ts` | Hand-written TypeScript declarations — keep in sync with the API. |
| `scripts/build-css.js` | Compiles SCSS → `dist/tabar.css` + `src/styles.js`. |
| `scripts/build.js` | esbuild bundler producing the `dist/` JS artifacts. |
| `scripts/build-site.js` / `scripts/serve.js` | Build the `site/` → `site/dist/`, and serve it. |
| `test/*.test.js` | Unit/DOM tests (`tabar`, `group`, `terminal`). |
| `e2e/*.spec.js` | Playwright browser tests — `visual` (screenshots) + `playground` (clicks). |
| `playwright.config.js` | Playwright config (serves the built site, light/dark projects). |
| `site/`, `examples/` | The marketing site (landing + playground + `visual.html`) and framework integrations. |

Styling changes go in `src/tabar.scss`; run `npm run styles` (or `npm run build`) to
regenerate `dist/tabar.css` and `src/styles.js`.

**Naming & CSS architecture.** The library uses **BEM** (`tabar`, `tabar__bar`,
`tabar-group__child`) plus `data-*-tabar` hooks, and depends on **no CSS framework** — keep it
that way (nothing in `src/` may reference Bootstrap/Webpixels/Tailwind). The **demo site** is a
separate concern: it's built with **Webpixels CSS** (Bootstrap-based) and uses its
utility/component classes (`btn`, `card`, `form-control`, `d-flex`, …); `build-site.js` vendors
`@webpixels/css` into `site/dist/assets/css/webpixels.css`, and `site/assets/scss/styles.scss`
holds only the few demo-specific bits the framework can't express. `site/visual.html` is a
self-contained Playwright fixture — it loads **neither** stylesheet so the screenshot baselines
stay stable when the demo's styling changes.

## Coding conventions

- **No runtime dependencies.** Dev-only tooling is fine; `src/` must stay dependency-free.
- **Security first.** Build DOM with `createElement`/`textContent` — never `innerHTML`. Apply
  styles with `el.style.setProperty(...)`, never by concatenating CSS strings. Sanitize any
  value used in a class name, attribute or selector. Treat stored data as untrusted: parse
  defensively, validate the shape and schema version, and clamp.
- **Keep it accessible.** Maintain `role="progressbar"`/`aria-*`, reduced-motion handling,
  and RTL behavior.
- Two-space indentation, semicolons, single quotes (`npm run lint`).
- Update `types/*.d.ts` and the docs whenever the public API changes.

## Tests

Add or update tests in `test/` for any behavior change. Cover edge cases (clamping,
concurrency, teardown, persistence validation). Run `npm test` before opening a PR.

### Browser & visual tests (Playwright)

`e2e/` holds Playwright specs that run against the built demo site:

- `e2e/visual.spec.js` snapshots the deterministic gallery at `site/visual.html`
  (every theme/state/shape at a fixed value — no timers, no transitions).
- `e2e/playground.spec.js` clicks every playground control and asserts there are no
  console errors.

```bash
npm run test:e2e          # serves the site and runs Chromium (light + dark)
```

**Visual snapshots are platform-sensitive.** The authoritative baselines are the
Linux ones (`e2e/**/*-snapshots/*-linux.png`) — the same ones CI compares against.
Regenerate them through the official Playwright container so they match CI exactly
(local macOS/Windows renders differ and would drift):

```bash
docker run --rm -v "$PWD:/work" -v /work/node_modules -w /work \
  mcr.microsoft.com/playwright:v1.61.0-jammy \
  bash -c "npm ci && npm run test:e2e:update"
```

(The `-v /work/node_modules` anonymous volume keeps your host `node_modules`
untouched.) When you add a new visual state, give it a tile in `site/assets/js/visual.js` and
regenerate the baselines. If you bump `@playwright/test`, update the image tag here
and in `.github/workflows/ci.yml`.

## Commits & pull requests

- Subject ≤ 72 chars, imperative mood; the body explains *why*.
- One logical change per PR; include a `CHANGELOG.md` entry under `[Unreleased]`.
- Make sure `npm test`, `npm run build` and `npm run lint` pass.

## Reporting bugs / requesting features

Use the GitHub issue templates. For security issues, **do not** open a public issue — see
[SECURITY.md](SECURITY.md).
